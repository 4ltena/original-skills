# Recovery and worktrees

Read this for a requested rollback, a dirty shared tree, parallel work, or cleanup. The active policy decides whether an operation is allowed; these steps choose a recoverable way to meet the request.

- To inspect an old revision, read its tree or use a separate worktree/branch when editing is needed. Record the current branch and HEAD before moving either. Do not interpret “show the previous version” as permission for `reset --hard`.
- A linked worktree shares repository administration with other worktrees. Record its path and branch, inspect `git worktree list`, and check its own status before removal. Do not manually delete it or force removal over user changes. Worktrees help separate long or concurrent tasks, but are not mandatory for a small isolated edit.
- `stash push` stores selected local changes and resets the affected worktree paths; it does not preserve where a branch points. Record the stash identifier and exact included paths. `apply` keeps the stash entry; `pop` removes it after successful application. Avoid dropping or clearing entries until recovery is verified. A stash is not a substitute for saving commits before a history rewrite.
- `restore`, `reset --hard` and `clean` can overwrite tracked or untracked work. Examine the exact paths and whether any change belongs to the user or another agent. Keep a verified copy when loss is possible, explain the effect, and get the active policy's approval before the destructive operation.
- If a published commit is wrong, consider a new revert commit to preserve shared history. Rewriting that history, including `--force-with-lease`, remains subject to its separate authorization and current remote state.
- If a real credential was committed or published, avoid printing it again. Treat it as compromised, alert the owner through an authorized channel, and arrange revocation or rotation with the provider. Removing it in a later commit or reverting the commit does not erase the earlier Git object. Any history cleanup is a separate, coordinated and policy-gated operation; do not force-push as an automatic repair.
- After an interrupted or failed command, inspect status, branch/HEAD, index, stash/worktree list or reflog as relevant, and the remote when publication was attempted. Preserve evidence and existing work. Diagnose before retrying or issuing a second mutation; an attempted command or success-looking text is not enough to claim completion.

Git command semantics: [worktree](https://git-scm.com/docs/git-worktree), [stash](https://git-scm.com/docs/git-stash), [reset](https://git-scm.com/docs/git-reset), [restore](https://git-scm.com/docs/git-restore), [clean](https://git-scm.com/docs/git-clean), [reflog](https://git-scm.com/docs/git-reflog), [revert](https://git-scm.com/docs/git-revert), [push](https://git-scm.com/docs/git-push). For an exposed credential, see [GitHub's remediation guidance](https://docs.github.com/en/code-security/tutorials/remediate-leaked-secrets/remediating-a-leaked-secret).
