# Browser storage / local-first / lifecycle

For G4/G5. Apply [Permanence/recovery contract](durability-and-recovery.md) first, and add browser-specific constraints in this section.

## 1. Select a Store by purpose

| Store | Main properties| Precautions when selecting|
|---|---|---|
| localStorage / sessionStorage | Web Storage synchronization key-value| Don't put mass serialize/write on UI hot path. Persistence and scope are not the same. |
| IndexedDB | async API indexed object store/transaction| index, query range, batch, transaction lifetime. It's not SQL. |
| OPFS | origin private file-oriented storage| byte I/O, handle/lock, quota, flush/close. It does not have SQL query functionality itself.|
| Cache API |Save Request/Response| Do not confuse the reacquirable resource cache with the unsynchronized domain original. |
| memory | Fast temporary state/index| Lost when process/lifecycle ends. Don't call it a persistent queue. |

Do not base your design budget on fixed values such as "1MB" or "1GB." Check the policy of the target browser/WebView and handle availability of `navigator.storage.estimate()`, approximate usage/quota, result of `persist()`, failure of quota/eviction/privacy mode. Even if the estimated free space is sufficient, it does not guarantee that subsequent writes will be successful. Persistent storage is not a backup for user deletion or device failure. [W20][H03][H05][H06]

## 2. Lifespan and completion of IDB transactions

Queue the necessary requests while the transaction is active and understand the auto-commit conditions. Don't await unrelated fetch/timers and assume you can use the same transaction afterwards. On the other hand, "transaction always dies in any await" is incorrect, so check the contract between the wrapper and request callback/microtask. [H03]

External I/O and heavy pre-computation are completed first, and within the transaction, the current revision is rechecked and only limited operations are performed. Large batches measure throughput and the amount of retries when waiting, memory, and aborting other operations, and do not pack them into one transaction indefinitely.

```js
// Auxiliary example of waiting for transaction completion. Register immediately after transaction generation.
function transactionDone(tx) {
  return new Promise((resolve, reject) => {
    tx.addEventListener('complete', () => resolve(), {once: true});
    tx.addEventListener('abort', () => {
      reject(tx.error ?? new Error('IndexedDB transaction aborted'));
    }, {once: true});
  });
}
```

The user must process this promise and also handle errors for individual requests. Request's `success` does not necessarily mean that the entire transaction has been committed. The `commit()` call itself is not a replacement for the completion event. `durability: strict/relaxed/default` checks the target implementation as a hint/contract difference. Just specifying strict does not declare unconditional power-loss safety. [H03]

If domain data and Outbox need to be stored atomically, update them with one readwrite transaction that includes the target object store in the same DB. Network transmission is done after commit. The final revision/receipt and Outbox completion processing after ACK are also made atomic. Do not treat different DBs as one transaction.

## 3. Schema migration and old tabs

Developer implements schema/data migration using `indexedDB.open(name, targetVersion)` and upgrade process. `onupgradeneeded` is not automatically generated by SQL migration. [H03]

- Implement close/reopen policy on `versionchange` for each connection and handle in-progress operations and unsaved UI.
- If the new version open is `blocked`, the reason and recovery UI will be displayed. Do not close old tabs without permission or delete unsynchronized DBs.
- Define conditions for old code to read/write new schema. Explicitly handles open failures specified by older versions.
- For destructive changes, consider export/backup/stage migration and test recovery from interruptions and quota shortages. Do not replace the original migration just by clearing the cache.

Do not include network waits in upgrade transactions. For long data conversions, a design in which schema and data revision are separated and executed in stages is a candidate, but read/write compatibility during conversion and restart position should be defined first.

## 4. OPFS and SQLite/Wasm

`FileSystemSyncAccessHandle` is an API exposed to DedicatedWorker, so it is not assumed that it can be used by ServiceWorker. It also doesn't mean that you can move sync I/O to the UI thread. Check the target browser, worker context, handle lock, flush/close, and unfinished writes that are being completed. [H05]

When using SQLite/Wasm, check the combination of Wasm engine and OPFS VFS, synchronization method, locking, multiple connections/tabs, and isolation requirements for each VFS. Just because it supports OPFS does not mean that all SQLite VFS can be used. Choose IDB or SQLite, including query/schema/index, migration, binary workload, and deployment complexity. [H23]

SQL transaction commit, VFS flush, file replace, and hardware persistence are not on the same abstraction layer. Remove unidentified layers from warranty coverage to avoid excessive durability claims. [H20]

## 5. sync owner of multiple tabs

We will compare the idea of sharing the connection with SharedWorker, etc., the idea of serializing sync within the same scope with Web Locks, and the idea of using each tab transmission + server idempotency. Simply declaring "I am a leader" in BroadcastChannel does not guarantee exclusiveness. Channels are not treated as durable logs either. [H07][H12]

Check the scope of lock/worker using storage partition, origin, and client conditions. Local exclusion is not business exclusion for multiple devices or servers. Test suspend/resume, lock retention, leadership change, return of old leader, account switch, and connection disconnection. Specify fallback when there is no API to use, and avoid deteriorating UI/energy due to busy polling.

## 6. Service Worker / deployment

ServiceWorker's lifetime is tied to event processing and can be stopped when it is idle, etc. Event contracts such as `waitUntil` also do not guarantee permanent residence. Check the presence and execution conditions of the background sync API, and leave a path to collect the Outbox when the foreground is restarted. [H08]

Create a compatibility table for app build, worker script, message protocol, DB schema, and cache version. The new version that is waiting and the old client that is running can coexist. Don't hide the mix by adding `skipWaiting`/`clients.claim` unconditionally. [H24]

Cache cleanup targets only resources that can be retrieved again, and takes into account resources being referenced by the current/old client and offline usage conditions. Deletion of storage related to unsynchronized DB and authorization will not be performed without permission as a performance optimization. When changing CSP/COOP/COEP/third-party/OAuth popup/WebView deployment, conduct a separate compatibility and security review. [H11]

## 7. Required measurements and tests

What we measure: transaction wait/duration, number of requests, commit observations, index/query cost, serialize bytes, outbox age/retry/conflict, storage usage, UI apply. network RTT alone does not explain the whole local-first.

Select F04 to F11 to apply from [fault tests](failure-injection.md) and reopen with the actual browser profile. Don't just take the list visible in DevTools as the original, check the revision/record set read from the application and the receipt. Do not conclude from the lecture alone that a particular DevTools bug still exists.
